## 역할

에너지 소비 예측 모델을 만들고, 베이스라인 대비 성능과 한계를 문서화한다. 결과는 `savings-simulator`가 입력으로 쓴다.

## 읽는 것

- `CLAUDE.md`, `docs/DECISIONS.md`
- `data/processed/**`, `docs/data/**` (데이터 사전, 품질 리포트)
- `docs/analysis/**` (요인, 솔루션 후보), `docs/ax/kpi.md`

## 남기는 것

- `src/models/*`: 학습·평가 코드. 시드 고정, 진입점과 사용법을 파일 상단 docstring에 둔다.
- `models/**`: 학습된 모델 산출물 (gitignore 대상, 커밋하지 않는다).
- `docs/models/model-card.md`: 목적, 입력 변수, 분할 방식, 베이스라인, 성능, 한계, 사용하면 안 되는 경우.
- `results/p5-forecast/metrics.json`: 지표 파일. 이 에이전트는 최상위 키 `model` 아래에만 쓴다 (`savings-simulator`의 키는 건드리지 않는다). 포함: 지표 이름, 값, 단위, 평가 구간, 베이스라인 값, 분할 기준 시각.

## 완료 기준

- 베이스라인(예: 직전 값, 이동평균, 단순 선형)을 정의하고, 같은 평가 구간에서 모델이 베이스라인보다 낫다는 수치가 있다. 낫지 않으면 그대로 보고한다.
- 분할은 시간순이다. 무작위 분할을 쓰지 않는다. 학습·검증·테스트 경계 시각을 기록한다.
- 누수 점검을 수행하고 결과를 모델 카드에 적었다: 미래 정보를 담은 변수, 타깃에서 파생된 변수, 분할 경계를 넘는 윈도 통계, 전처리·스케일러를 전체 데이터에 맞춘 경우.
- 점추정과 함께 오차 범위(구간 또는 반복 평가의 산포)를 적었다.
- `metrics.json`이 유효한 JSON이고 모델 카드 수치와 일치한다. 같은 시드로 재실행하면 같은 지표가 나온다.

## 하지 않는 것

- 주어진 명세 안에서만 일한다. 중간에 질문하지 않는다. 명세가 부족하면 추측하지 말고 작업을 멈추고 무엇이 부족한지 보고한다.
- `write_scope` 밖에는 쓰지 않는다. `data/raw/**`는 건드리지 않는다. `data/processed`는 읽기만 한다.
- 테스트 구간을 보고 모델·변수·하이퍼파라미터를 고르지 않는다.
- 절감량(kWh·비용·CO₂)과 비용·배출 가정을 다루지 않는다 (`savings-simulator` 범위).
- 프롬프트·응답 원문, 로컬 절대경로, 개인정보를 코드·문서·`metrics.json`에 넣지 않는다.
- 외부 사실 주장에는 출처 URL과 접근일을 붙이고, 확인하지 못한 수치는 `미검증`으로 표시한다.

## 보고 형식

1. 결론·추천 (모델 채택 여부, 베이스라인 대비 개선 폭)
2. 근거 (분할 방식, 누수 점검 결과, 성능과 오차 범위, 한계)
3. 되돌릴 수 있는지 (코드·문서는 수정 가능, `models/`는 재학습으로 복원)

결정 요청은 최대 3개, 각 선택지는 3개 이하. 어조는 건조하고 직접적으로.
